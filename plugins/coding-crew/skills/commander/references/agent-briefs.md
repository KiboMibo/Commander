# Брифы для субагентов

Субагент стартует с чистого контекста. Он не видел диалога с пользователем, не читал план, не знает, какая идёт волна и кто работает рядом. Всё, что он знает, — то, что написано в брифе.

Отсюда правило, которое экономит больше всего времени: **бриф должен быть самодостаточным.** Не «сделай T3», а постановка, по которой можно работать, ничего не додумывая. Проверь себя вопросом: сможет ли агент, не задавая ни одного вопроса, понять, что именно делать, какие файлы его, чем проверяется результат и куда класть отчёт?

## Обязательные части любого брифа

| Часть | Зачем |
|-------|-------|
| Какой скилл использовать | Без явного указания агент будет решать задачу «как обычно», мимо дисциплины скилла |
| Путь к плану и ID задачи | Источник правды; агент читает свою секцию сам, целиком |
| Границы файлов (владеет / только читает) | Единственное, что защищает параллельных агентов друг от друга |
| Имя ветки и базовая ветка | Иначе каждый выберет своё, и волна не соберётся |
| Путь для отчёта | Иначе каждый скилл выберет место по умолчанию, и вердикт придётся искать по репозиторию |
| Что вернуть в ответе | Тебе нужен короткий машинно-читаемый итог, а не пересказ работы |
| Соседи по волне | Чтобы агент понимал, почему нельзя лезть в соседние файлы |

## Как передать вызов скилла

В брифе прямо укажи, чем работать:

```
Используй скилл /coding-writer (инструмент Skill, имя `coding-writer`).
Если скилл в твоей сессии недоступен — прочитай его инструкции из
/root/.claude/skills/coding-writer/SKILL.md и следуй им.
```

Путь подставляй актуальный для среды — проверь, где лежат скилы, до первого запуска.

## Шаблон: исполнитель (`/coding-writer`)

```
Ты — кодинг-агент-исполнитель в команде, работающей по плану. Работаешь параллельно
с другими агентами, которые сейчас правят соседние файлы и не видят твоих изменений.

Скилл: /coding-writer (инструмент Skill, имя `coding-writer`). Если недоступен —
читай /root/.claude/skills/coding-writer/SKILL.md и следуй ему.

План: docs/plans/2026-07-31-scraper.md
Задача: T3 — прочитай её секцию в плане целиком, а также разделы «Контекст»,
«Архитектурные решения» и «Контракты».

Файлы, которыми ты владеешь: src/scraper/fetch.ts, src/scraper/fetch.test.ts
Файлы, которые только читаешь: src/types.ts, src/config.ts
В остальные файлы не пиши. Соседи по волне: T4 (владеет src/scraper/parse.ts),
T5 (владеет src/cli.ts). Их изменений ты не увидишь — это нормально.

Ветка: feat/T3-fetch от wave/scraper-w1. Создай её сам, коммить по ходу,
запушь в конце. PR не открывай — ветки волны сведёт командир.

Отчёт: docs/reports/T3-2026-07-31.md по шаблону скилла.

Верни в финальном сообщении (это твой возвращаемый результат, не обращение к человеку):
- статус: DONE / BLOCKED
- ветка и список коммитов
- путь к отчёту
- по каждому критерию приёмки из плана — чем именно подтверждён
- что осталось незакрытым и почему
- вопросы, требующие решения человека, если есть

Если упрёшься в точку остановки из скилла — не выдумывай обход. Верни BLOCKED
с конкретикой: что мешает, какие варианты видишь.
```

## Шаблон: тесты (`/coding-test`)

```
Ты — тестовый инженер, проверяешь волну 1 плана docs/plans/2026-07-31-scraper.md.
Вызов делегированный: спрашивать некого, спорные решения принимай сам и записывай
их в раздел «Допущения» отчёта.

Скилл: /coding-test (инструмент Skill, имя `coding-test`).

Область проверки: файлы, которыми владеют задачи T3, T4, T5 (см. их секции в плане).
Критерии приёмки бери из плана, а не придумывай свои.
Продакшн-код не правь — ты владеешь только тестовыми файлами и тестовой
инфраструктурой. Падающий тест — это находка для отчёта, а не повод чинить код.

Ветка: test/R1-tests от wave/scraper-w1.
Отчёт: docs/plans/reviews/scraper-R1-test.md и .json рядом.

Верни: статус (PASS / PASS_WITH_FINDINGS / FAIL / BLOCKED), число написанных и
упавших тестов, покрытие изменённого кода, список блокирующих находок с файлом
и строкой, путь к отчёту.
```

## Шаблон: секьюрити (`/coding-secure`)

```
Ты — секьюрити-ревьюер, проверяешь волну 1 плана docs/plans/2026-07-31-scraper.md.
Вызов делегированный, вопросы задавать некому.

Скилл: /coding-secure (инструмент Skill, имя `coding-secure`).

Область: код, изменённый задачами T3, T4, T5. Код не правь — только читай и пиши отчёт.
Отчёт: docs/plans/reviews/scraper-R1-sec.md

Верни: число находок по уровням (блокирующая / важная / замечание), список
блокирующих в виде, готовом перенести в задачу исправления (файл, строка, чем
грозит, что сделать), путь к отчёту. Пустой список блокирующих — нормальный
результат, не добирай объём.
```

## Шаблон: QA (`/coding-qa`)

```
Ты — QA-инженер, принимаешь волну 1 плана docs/plans/2026-07-31-scraper.md.
Вызов делегированный.

Скилл: /coding-qa (инструмент Skill, имя `coding-qa`).

Область: результат задач T3, T4, T5. Проверь по критериям приёмки из плана,
включая краевые случаи; оцени качество кода и тестов.
Продакшн-код не правь. [Если план разрешает дописывать тесты и докстринги —
скажи об этом здесь явно, иначе агент будет действовать по умолчанию скилла.]

Отчёт: docs/plans/reviews/scraper-R1-qa.md

Верни: вердикт (готово / готово с замечаниями / не готово), 3–5 главных находок
с уровнем серьёзности, что сделал своими руками, путь к отчёту.
```

## Шаблон: исправления (`F<N>`)

Задача исправления ставится тому же типу агента, что и реализация, но с готовым списком находок — не заставляй его перечитывать три отчёта целиком.

```
Скилл: /coding-writer.
Задача: F1 — устранить блокирующие находки проверочной волны 1.
План: docs/plans/2026-07-31-scraper.md

Находки (полные формулировки из отчётов, а не пересказ):
1. [sec, блокирующая] src/scraper/fetch.ts:42 — URL из аргумента подставляется
   в запрос без валидации схемы, возможен file:// и SSRF.
   Отчёт: docs/plans/reviews/scraper-R1-sec.md
2. [test, FAIL] src/scraper/parse.test.ts:88 — пустой HTML приводит к TypeError
   вместо пустого массива; критерий приёмки T4 требует пустой массив.
   Отчёт: docs/plans/reviews/scraper-R1-test.md

Файлы: те же, которыми владели T3, T4, T5.
Ветка: fix/F1-wave1 от wave/scraper-w1.
Отчёт: docs/reports/F1-2026-07-31.md

Верни: статус, по каждой находке — как закрыта и чем подтверждена, что не закрыто и почему.
```

## Частые ошибки в брифах

**Пересказ задачи вместо ссылки на неё.** Пересказ расходится с планом, и агент получает две версии правды. Дай путь и ID — он прочитает первоисточник.

**Молчание о границах файлов.** Самая дорогая ошибка: агент честно делает работу, попутно правит соседний файл, и труд параллельного агента теряется при мерже.

**Отсутствие требований к возвращаемому результату.** Без них агент вернёт человеко-ориентированный рассказ, и статус волны придётся вычитывать из прозы.

**Запрос разрешения у агента.** Субагент не может ничего спросить: диалога у него нет. Всё, что требует решения, решай до запуска или принимай на себя после отчёта.

**Слишком широкая задача.** «Сделай всю волну одним агентом» стирает границы владения и убивает параллелизм ради экономии одного вызова.

**Перепрогон в тот же файл отчёта.** Запуская проверяющего второй раз после `F<N>`, дай ему путь с суффиксом круга (`…-R2-sec-round2.md`) и скажи, что это второй круг и какие находки чинились. Иначе он затрёт отчёт первого круга, и доказательство найденного дефекта исчезнет вместе с ним.
