# Git-модель командира

Командир владеет структурой веток и мержем. Исполнители владеют только своими ветками задач.

## Иерархия

```
main / master                    мерж только с разрешения пользователя
  └── develop                    рабочая ветка; командир мержит сюда сам
        └── wave/<слаг>-w<N>     интеграционная ветка волны
              ├── feat/T3-…      ветки задач (создают исполнители)
              ├── feat/T4-…
              └── fix/F1-wave1   ветка исправлений после проверочной волны
```

Смысл промежуточной ветки волны: собрать и проверить результат нескольких агентов до того, как он попадёт в рабочую ветку. Проверочная волна гоняется именно на ней — так `develop` никогда не содержит непроверенного кода, а неудачную волну можно выбросить одной командой, не разбирая, чей коммит что сломал.

Для одной задачи в волне промежуточная ветка не нужна — ветка задачи и есть ветка волны.

## Настройка перед стартом

```bash
git rev-parse --is-inside-work-tree     # репозиторий вообще есть?
git remote -v                            # remote и платформа
git status --porcelain                   # чужие незакоммиченные изменения
git branch -a                            # какие ветки уже есть
```

Чужие незакоммиченные изменения в рабочем дереве — **точка остановки**. Не коммить и не сбрасывай их: пользователь мог оставить их намеренно.

Создание рабочей ветки, если её нет:

```bash
git fetch origin
git switch -c develop origin/main    # или от master
git push -u origin develop
```

Ветка волны — от актуальной рабочей:

```bash
git switch develop && git pull --ff-only
git switch -c wave/scraper-w2
git push -u origin wave/scraper-w2
```

Пушить ветку волны до запуска агентов стоит: исполнители ответвляются от неё, и remote-версия избавляет от расхождений.

## Новый репозиторий

Точка остановки — спроси имя и приватность до создания.

```bash
git init && git add -A
git commit -m "chore: initial commit"
gh repo create <owner>/<name> --private --source=. --remote=origin --push
```

Приватный по умолчанию: код, о публичности которого не договаривались, лучше не публиковать. Нет `gh` или нет авторизации — скажи об этом, работай локально и дай пользователю точные шаги для создания remote вручную.

Полезно сразу: `.gitignore` под стек, `README.md` заглушкой (наполнит `/coding-qa` в конце), базовая ветка `develop`.

## Сбор волны

После того как все исполнители волны отчитались:

```bash
git switch wave/scraper-w2 && git pull --ff-only
git merge --no-ff feat/T3-fetch -m "merge(T3): загрузка страниц"
git merge --no-ff feat/T4-parse -m "merge(T4): парсинг карточек"
git push
```

`--no-ff` сохраняет границы задач в истории — по ней видно, что сделал каждый агент, и легко откатить одну задачу целиком.

Прогони тесты и сборку на собранной ветке **до** запуска проверочной волны: смысл проверочных агентов в том, чтобы смотреть на совместный результат, а не на сумму отдельных.

## Конфликты

Конфликт при сборке волны — почти всегда дефект плана: две задачи владели одним файлом. Порядок действий:

1. Разреши конфликт сам, если правки очевидно независимы (разные функции в одном файле, разные ключи в конфиге).
2. Почини план: разведи задачи по волнам или объедини их, чтобы это не повторилось.
3. Запиши в борд, что конфликт был и как разрешён — проверяющим важно знать, что этот файл собирался руками.
4. Если правки противоречат друг другу по существу (обе меняют одну логику по-разному) — это не мерж, а вопрос: чья версия верна. Верни задачу исполнителю с обеими версиями либо останови и спроси.

Никогда не разрешай конфликт выбором «взять свою» без чтения обеих сторон — так теряется работа целого агента.

## Мерж в рабочую ветку

Только после зелёного вердикта волны:

```bash
git switch develop && git pull --ff-only
git merge --no-ff wave/scraper-w2 -m "merge(wave 2): загрузка и парсинг"
git push
```

Если ветка защищена или в проекте принят PR-флоу — не обходи правила: открой PR и мержи через него.

```bash
gh pr create --base develop --head wave/scraper-w2 \
  --title "Волна 2: загрузка и парсинг" --body-file docs/plans/state/scraper-status.md
gh pr merge --merge   # squash/rebase — по конвенции проекта
```

GitLab — `glab mr create` / `glab mr merge`. Нет CLI — дай пользователю ссылку, которую remote возвращает в ответе на push.

Мерж заблокирован защитой ветки, требующей ревью человека, — это не ошибка и не повод искать обход. Оставь PR открытым, запиши в борд и продолжай следующую волну, если она не зависит от мержа.

## Мерж в основную ветку

Точка остановки. Перед вопросом пользователю подготовь: что вливается (`git log --oneline develop ^main`), какие вердикты собраны, что отложено. Спрашивай один раз в конце плана, а не после каждой волны.

## Чего не делать

- `push --force` в любую ветку, кроме своей только что созданной, и то с `--force-with-lease`.
- `reset --hard` поверх незакоммиченных изменений.
- Удалять ветки с несмерженной работой — даже неудачная волна это данные для разбора.
- Коммитить `.env`, ключи, дампы, большие бинарники.
- Работать напрямую в `main`/`master`/`develop`: тогда нечего ревьюить и некуда откатываться.
