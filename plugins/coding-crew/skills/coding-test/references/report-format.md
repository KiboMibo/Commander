# Формат отчётов

Два файла с одинаковым именем и разными расширениями. Markdown читает человек, JSON читает вызвавший агент — не заставляй его парсить прозу, но и не превращай Markdown в дамп JSON'а.

Оба файла описывают один и тот же прогон: если статусы или числа в них разойдутся, доверять перестанут обоим.

---

## Markdown-отчёт

Язык — язык диалога с пользователем. Пути, имена тестов, команды и идентификаторы из кода — как в репозитории.

Разделы, которых нет (нет находок, нет допущений), не выкидывай молча — пиши «нет». Пустой раздел говорит «проверено, чисто»; отсутствующий раздел говорит «забыли».

```markdown
# Тесты: <что покрывали> — <статус>

- **Дата:** 2026-07-31
- **Статус:** FAIL
- **Скоуп:** волна 2 плана `2026-07-28-user-auth.md` — `src/api/auth/login.ts`, `src/lib/jwt.ts`
- **Команда прогона:** `npm test -- src/api/auth`

## Итог

Две-три строки: что покрыто, что нашлось, что делать дальше. Это единственное,
что прочитают в 80% случаев, — пиши так, чтобы решение принималось отсюда.

## Что покрыто

| Файл | Тесты | Кейсы |
|------|-------|-------|
| `src/api/auth/login.ts` | `src/api/auth/login.test.ts` | успешный вход, неверный пароль, несуществующий email, отсутствующее поле, повторный вход |
| `src/lib/jwt.ts` | `src/lib/jwt.test.ts` | подпись, срок годности, испорченный токен |

Добавлено тестов: 14 (unit 11, интеграционных 3).

## Результат прогона

- Базовый прогон (до работы): 128 passed, 0 failed
- Итоговый прогон: 140 passed, 2 failed
- Стабильность: 3 прогона подряд, результат одинаковый

Падающие тесты:

- `login.test.ts › returns_401_for_unknown_email` — ожидался 401, получен 404
- `jwt.test.ts › rejects_expired_token` — истёкший токен принимается

## Покрытие

- Изменённые строки: **83%** (порог 80%) — 96 из 116
- По репозиторию: 71% (справочно)

Непокрытые изменённые строки и почему:

- `src/lib/jwt.ts:88-94` — ветка для алгоритма `RS256`, не используется в текущей конфигурации; покрывать имеет смысл вместе с задачей по ротации ключей.

## Находки

### 1. Неизвестный email возвращает 404 вместо 401 — блокирующая

- **Где:** `src/api/auth/login.ts:42`
- **Чем грозит:** ответ различает «нет такого пользователя» и «неверный пароль», что позволяет перебором собрать список зарегистрированных адресов. Расходится с критерием приёмки T3.
- **Предлагается:** возвращать 401 и то же тело, что при неверном пароле.
- **Тест:** `login.test.ts › returns_401_for_unknown_email` (падает)

### 2. Истёкший токен принимается — блокирующая

- **Где:** `src/lib/jwt.ts:61`
- **Чем грозит:** `exp` не проверяется, сессия живёт вечно.
- **Предлагается:** проверять `exp` при верификации.
- **Тест:** `jwt.test.ts › rejects_expired_token` (падает)

### 3. `login` тянет три зависимости напрямую — замечание

- **Где:** `src/api/auth/login.ts:1-12`
- **Чем грозит:** для теста приходится мокать БД, часы и логгер; это признак того, что зависимости стоит передавать снаружи.
- **Предлагается:** вынести в параметры или фабрику при следующем касании файла.

## Чувствительность тестов

Точечная проверка: у 6 ключевых тестов временно вносился дефект в проверяемую
логику, все 6 покраснели. Продакшн-код возвращён в исходное состояние
(`git status` чист).

Не переспецифицированы: на временной копии репозитория с предлагаемыми правками
(находки 1 и 2) набор зелёный целиком — задаче F2 не придётся править тесты.

Mutation-тестирование: Stryker в проекте не настроен, не проводилось.

## Допущения

- Сценарий «пользователь заблокирован» не покрыт: в коде волны его нет, критерий приёмки не упоминает.
- Интеграционные тесты используют sqlite вместо postgres — так уже сделано в существующих тестах проекта.

## Было сломано до начала работы

Нет.
```

## JSON-сводка

Тот же файл, что и Markdown, но с расширением `.json`. Держи его маленьким: он нужен для решения «дальше / чинить / звать людей», а не для чтения вместо отчёта.

```json
{
  "skill": "coding-test",
  "status": "FAIL",
  "date": "2026-07-31",
  "scope": {
    "source": "plan:docs/plans/2026-07-28-user-auth.md#R2-test",
    "files": ["src/api/auth/login.ts", "src/lib/jwt.ts"]
  },
  "tests": {
    "added": 14,
    "run_command": "npm test -- src/api/auth",
    "baseline": { "passed": 128, "failed": 0 },
    "final": { "passed": 140, "failed": 2 },
    "failing": [
      "login.test.ts › returns_401_for_unknown_email",
      "jwt.test.ts › rejects_expired_token"
    ],
    "flaky": []
  },
  "coverage": {
    "changed_lines_pct": 83,
    "threshold": 80,
    "threshold_met": true,
    "repo_pct": 71
  },
  "findings": [
    {
      "severity": "blocking",
      "title": "Неизвестный email возвращает 404 вместо 401",
      "file": "src/api/auth/login.ts",
      "line": 42,
      "impact": "Перебором можно собрать список зарегистрированных адресов; расходится с критерием приёмки T3.",
      "suggestion": "Возвращать 401 с тем же телом, что при неверном пароле.",
      "test": "login.test.ts › returns_401_for_unknown_email"
    }
  ],
  "sensitivity_check": {
    "spot_check": { "tests_checked": 6, "detected_defect": 6 },
    "not_overspecified": { "checked": true, "green_after_fix": true },
    "mutation": { "run": false, "reason": "инструмент в проекте не настроен" }
  },
  "report_md": "docs/plans/reviews/user-auth-R2-test.md",
  "next_action": "Завести задачу F2 на находки 1-2; следующую волну не начинать."
}
```

### Поля

| Поле | Обязательное | Смысл |
|------|--------------|-------|
| `status` | да | `PASS` / `PASS_WITH_FINDINGS` / `FAIL` / `BLOCKED` |
| `scope.source` | да | Откуда взят скоуп: `plan:<путь>#<задача>`, `git-diff:<база>`, `explicit` |
| `tests.baseline` | да | Результат прогона до работы — без него падения нельзя атрибутировать |
| `tests.flaky` | да | Тесты, мигавшие между прогонами; пустой список — валидный ответ |
| `coverage.changed_lines_pct` | да | Покрытие изменённых строк; `null`, если посчитать не удалось (тогда `notes` с причиной) |
| `coverage.basis` | если diff неинформативен | Что считали вместо изменённых строк и почему — например `"файлы скоупа целиком: в репозитории один коммит"` |
| `tests.known_defect_marked` | если тесты помечены маркером | Список тестов, оставленных не-красными по договорённости, чтобы они не потерялись |
| `findings[].severity` | да | `blocking` / `important` / `note` |
| `sensitivity_check` | да | Чем подтверждено, что тесты ловят дефекты |
| `next_action` | да | Одна фраза: что делать вызвавшему |
| `blocked_reason` | если `BLOCKED` | Что именно помешало и что нужно от человека |

Если статус `BLOCKED`, поля про тесты и покрытие могут быть `null` — важно, чтобы `blocked_reason` объяснял, на каком шаге всё встало.
