# Сканеры: установка, запуск, разбор вывода

Сканеры дают воспроизводимость и базу CVE, которой у модели в голове нет. Но их вывод — сырьё: он не знает архитектуру проекта, не отличает продакшен от фикстуры и склонен к ложным срабатываниям. Всё, что отсюда получено, проходит фазу верификации.

Скрипт `scripts/scan.sh` делает всё описанное ниже автоматически (`$OUT` — его каталог вывода, по умолчанию `/tmp/coding-secure-scan-<имя-репо>`, вне проверяемого репозитория). Этот файл нужен, когда скрипт не сработал, инструмент требует нестандартных флагов или нужно разобрать конкретное срабатывание.

## Общие правила

**Ставь только то, что нужно для найденного стека.** Установка всех сканеров подряд на проект из одного `go.mod` — потерянные минуты.

**Всегда пиши вывод в файл**, а не только в терминал: `$OUT/<tool>.json`. Полный JSON часто нужен второй раз — уточнить строку, версию, идентификатор CVE, — а повторный прогон дорогой.

**Проверяй код возврата отдельно от наличия находок.** У большинства сканеров ненулевой код означает «нашёл проблемы», а не «упал». Различать их надо по тому, есть ли валидный JSON на выходе. В скриптах — `|| true` плюс проверка файла.

**Ограничивай область.** Почти все инструменты по умолчанию идут по всему дереву, включая `node_modules`, `vendor`, `.venv`, `dist`, снапшоты тестов. Это и медленно, и шумно. Исключай сборочные и вендорные директории явно.

**Фиксируй, что не отработало.** Если `trivy` не смог скачать базу из-за сети — это строка в разделе «Не проверено», а не молчаливый пропуск.

## Секреты: gitleaks

Установка:

```bash
# Linux x64
curl -sSL https://github.com/gitleaks/gitleaks/releases/latest/download/gitleaks_$(curl -s https://api.github.com/repos/gitleaks/gitleaks/releases/latest | grep -oP '"tag_name": "v\K[^"]+')_linux_x64.tar.gz | tar -xz -C /usr/local/bin gitleaks
# macOS
brew install gitleaks
```

Рабочее дерево (режим диффа и заданного набора):

```bash
gitleaks detect --no-git --source . --report-format json --report-path $OUT/gitleaks.json --redact || true
```

Вся история (только при полном аудите — на больших репозиториях это минуты):

```bash
gitleaks detect --source . --report-format json --report-path $OUT/gitleaks-history.json --redact || true
```

`--redact` маскирует значения в отчёте. Используй его всегда: полный секрет не должен попасть ни в лог сессии, ни в файл отчёта, который потом закоммитят.

**Разбор.** Каждое срабатывание — объект с `File`, `StartLine`, `RuleID`, `Commit`, `Author`, `Date`. Ключевое поле для приоритизации — `Commit`: если он не пустой, секрет **в истории**, и находка автоматически означает ротацию ключа, а не просто удаление строки.

Типовые ложные срабатывания: примеры в `README` и документации, фикстуры в тестах, публичные ключи (не приватные), значения-плейсхолдеры вида `xxxxx`/`changeme`/`your-api-key-here`, base64 от неспециальных данных. Проверяй по имени файла, содержимому вокруг и тому, похоже ли значение на реальный формат ключа провайдера.

Обратная сторона: gitleaks ищет по шаблонам известных провайдеров и **пропускает самодельные секреты** — внутренние токены, пароли к БД, строки подключения нестандартного вида. Их ищи глазами: `grep` по `password`, `passwd`, `secret`, `token`, `api_key`, `connection_string`, `DSN`, `Authorization`, `Bearer`, а также по схемам URL с credentials (`://user:pass@`).

## Зависимости

### osv-scanner — основной, кросс-языковой

```bash
go install github.com/google/osv-scanner/cmd/osv-scanner@latest   # или бинарник из релизов
osv-scanner --format json --recursive . > $OUT/osv.json 2>/dev/null || true
```

Читает `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `poetry.lock`, `requirements.txt`, `go.mod`, `Cargo.lock`, `Gemfile.lock` и другие. Работает по lock-файлам — если lock-файла нет, покрытие резко хуже: скажи об этом в отчёте.

**Разбор.** `results[].packages[].vulnerabilities[]` — там `id` (GHSA/CVE), `summary`, `database_specific.severity`. Поле `affected[].ranges` показывает, с какой версии починено — это и есть цель обновления.

### Родные аудиты

```bash
npm audit --json > $OUT/npm-audit.json || true      # или pnpm audit --json / yarn npm audit --json
pip-audit --format json --output $OUT/pip-audit.json || true
govulncheck -json ./... > $OUT/govulncheck.json || true
cargo audit --json > $OUT/cargo-audit.json || true
```

`govulncheck` ценен тем, что делает анализ достижимости: показывает не «в модуле есть CVE», а «ваш код вызывает уязвимую функцию». Его вывод почти не требует фильтрации — если он говорит, что путь есть, это настоящая находка.

`npm audit` наоборот склонен к шуму: считает уязвимыми любые транзитивные зависимости, включая dev-only и те, чья уязвимая ветка кода недостижима. Смотри поле `dev` и не тащи dev-зависимости в блокирующие.

## Код

### semgrep

```bash
pip install semgrep --break-system-packages
semgrep --config=auto --json --output $OUT/semgrep.json \
  --exclude=node_modules --exclude=vendor --exclude=.venv --exclude=dist --exclude=build . || true
```

`--config=auto` подтягивает публичные правила под определённые языки. Для целевого прогона по конкретным классам: `--config=p/security-audit`, `p/secrets`, `p/owasp-top-ten`, `p/dockerfile`, `p/ci`.

**Разбор.** `results[]` с `check_id`, `path`, `start.line`, `extra.message`, `extra.severity`, `extra.metadata.cwe`. `ERROR` — не «критично», а «правило уверено в шаблоне»; серьёзность для отчёта определяй сам по достижимости, а не копируй из вывода.

Semgrep хорош на синтаксических шаблонах (конкатенация в SQL, `eval` от переменной, отключённая проверка TLS) и слеп к логике: он никогда не скажет, что эндпоинт не проверяет владельца объекта.

### bandit (Python)

```bash
pip install bandit --break-system-packages
bandit -r . -f json -o $OUT/bandit.json -x ./tests,./.venv || true
```

Известен ложными срабатываниями на `assert`, `random`, `subprocess` без `shell=True` и на `hashlib.md5` в некриптографическом использовании. Фильтруй: `-s B101` отключает проверку `assert`.

## Инфраструктура

```bash
trivy fs --format json --output $OUT/trivy-fs.json --scanners vuln,secret,misconfig . || true
trivy image --format json --output $OUT/trivy-image.json <образ> || true   # если образ собирается
pip install checkov --break-system-packages && checkov -d . -o json > $OUT/checkov.json || true
docker run --rm -i hadolint/hadolint < Dockerfile > $OUT/hadolint.txt || true
```

`trivy` требует сети для обновления базы уязвимостей при первом запуске. Если сети нет — база не скачается, и вывод будет пустым при нулевом коде возврата; это не «чисто», это «не проверено». Проверяй, что в JSON вообще есть `Results`.

`checkov` даёт много правил уровня «хорошая практика» (теги, шифрование логов). Для отчёта отбирай то, что связано с доступом извне и секретами: публичные бакеты, открытые в мир порты, отсутствие шифрования на данных, широкие IAM-политики.

## Если инструмент недоступен

Нет сети, нет прав на установку, платформа не поддерживается — ревью продолжается, меняется только глубина:

| Не работает | Чем заменить | Что записать в «Не проверено» |
|---|---|---|
| gitleaks | `grep` по типовым именам секретов и схемам URL с credentials; просмотр `.env*`, конфигов, CI-переменных | «Скан истории git на секреты не выполнялся» |
| osv-scanner / audit | сверка версий из lock-файла с известными проблемными релизами; `WebSearch` по `<пакет> <версия> CVE` для ключевых зависимостей | «Полная проверка CVE не выполнялась, проверены только N ключевых пакетов» |
| semgrep | чтение кода от точек входа по чек-листу стека | «Статический анализ шаблонов не выполнялся» |
| trivy / checkov | ручной разбор Dockerfile и манифестов по `checklist-infra.md` | «Автоматическая проверка конфигурации инфраструктуры не выполнялась» |

Ручной аудит без сканеров — нормальный результат, если честно обозначены границы. Молчаливый пропуск, который читатель примет за «проверено и чисто», — нет.
