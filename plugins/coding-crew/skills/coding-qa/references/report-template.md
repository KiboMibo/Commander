# Шаблон QA-отчёта

Структура ниже — ориентир, а не бланк. Разделы, по которым в этом прогоне сказать нечего, убирай целиком: пустая рубрика «Безопасность: не проверялось» создаёт иллюзию проверки. Порядок разделов менять не стоит — читатель отчёта обычно смотрит вердикт и блокирующие находки, а дальше уходит по своим делам.

Заполненный пример — после шаблона.

---

```markdown
# QA-отчёт: <что проверяли>

**Дата:** YYYY-MM-DD
**Область:** <волна плана / диапазон коммитов / модуль / весь проект>
**Вердикт:** готово / готово с замечаниями / не готово

## Резюме

Два-четыре предложения: что проверяли, что в итоге, на что смотреть в первую очередь.

## Что проверено

- Прогон тестов: `<команда>` — X прошло, Y упало, Z пропущено
- Линтер / типы: `<команда>` — результат
- Просмотрено вручную: <файлы, модули, стыки>
- Не проверено и почему: <например, интеграционные тесты не запускались — нет доступа к тестовой БД>

## Находки

### Блокирующие

1. **<Короткое название>** — `путь/к/файлу.ts:42`
   Что не так: ...
   Чем грозит: ...
   Предлагается: ...

### Важные

1. **<Название>** — `путь:строка`
   Что не так / чем грозит / предлагается

### Замечания

- `путь:строка` — краткая формулировка

## Тесты

**Результат прогона.** Команда, числа, время. Если тесты не удалось запустить — что именно помешало.

**Разбор падений.** По каждому упавшему: причина и класс (баг в коде / устаревший тест / флейк / окружение).

**Качество существующих тестов.** Что проверялось мутацией и как отреагировало; тесты, которые ничего не проверяют; заскипанные и почему.

**Покрытие стыков.** Таблица по найденным стыкам:

| Стык | Happy path | Ошибки границы | Краевые данные | Транзакции |
|---|---|---|---|---|
| `POST /api/orders` ↔ БД | есть | нет | частично | нет |

**Дописано.** Список новых тестовых файлов и что каждый проверяет. Отдельно — тесты, помеченные как ожидаемо падающие, со ссылкой на находку.

## Комментарии к коду

**Добавлено.** Где и что (по файлам, без пересказа содержимого).

**Исправлено.** Комментарии, которые описывали устаревшее поведение.

**Предлагается** (если файлы не трогали): `файл:строка` → предлагаемый комментарий.

## Документация

**Состояние.** Что есть, что устарело, чего нет. Для устаревшего — конкретно: «в README команда `npm run dev`, в `package.json` её нет».

**Создано / обновлено.** Список файлов.

**План генерации** (если писать сразу не стали): какие документы нужны, что в каждом, откуда материал, что требуется от человека, в каком порядке.

## Рекомендации

Три-семь пунктов в порядке приоритета: что сделать до релиза, что после. Каждый — с указанием, какую находку закрывает.
```

## Пример заполнения (фрагмент)

```markdown
# QA-отчёт: волна 2 плана user-auth

**Дата:** 2026-07-31
**Область:** задачи T3, T4 плана `docs/plans/2026-07-28-user-auth.md`
**Вердикт:** не готово

## Резюме

Логин и обновление токена реализованы, юнит-тесты зелёные. Блокирует одно:
интеграционных тестов на стык с БД нет вообще, а ручная проверка нашла
расхождение с критериями приёмки — несуществующий email отдаёт 404 вместо 401,
то есть по ответу можно перебирать зарегистрированные адреса. Дописал четыре
интеграционных теста; один из них падает и помечен `test.fail` — это находка B1.

## Что проверено

- Прогон тестов: `npm test` — 47 прошло, 0 упало, 3 пропущено
- Типы: `npm run typecheck` — чисто
- Просмотрено вручную: `src/api/auth/*`, `src/lib/jwt.ts`, стык с `users` в БД
- Не проверено: нагрузка и время ответа — вне области волны

## Находки

### Блокирующие

1. **Логин раскрывает существование аккаунта** — `src/api/auth/login.ts:38`
   Что не так: при неизвестном email возвращается 404 `{error: "user_not_found"}`,
   тогда как критерий приёмки T3 требует 401 с тем же телом, что и при неверном пароле.
   Чем грозит: перебором можно собрать список зарегистрированных адресов —
   готовая база для фишинга и credential stuffing.
   Предлагается: вернуть 401 `{error: "invalid_credentials"}` в обеих ветках;
   тест уже написан — `src/api/auth/login.integration.test.ts:61`, снять `test.fail`.

### Важные

1. **Ошибка БД проглатывается** — `src/api/auth/refresh.ts:24`
   Что не так: `catch (e) { return null }` — недоступность БД неотличима от
   невалидного токена.
   Чем грозит: во время сбоя БД все пользователи молча разлогиниваются,
   в логах пусто, инцидент диагностируется вслепую.
   Предлагается: логировать с контекстом и отдавать 503 на ошибках инфраструктуры.
```
