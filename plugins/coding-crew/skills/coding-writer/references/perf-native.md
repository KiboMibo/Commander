# Производительность и память: Go, Rust, C/C++

Порядок работы всегда один: **воспроизведи → измерь → почини → измерь снова**. В системных языках соблазн угадать особенно велик, а промах особенно дорог: оптимизация вслепую усложняет код, ломает читаемость и нередко замедляет из-за промахов кеша. Оба числа, до и после, полученные одинаково, идут в отчёт.

---

## Go

### Измерение

| Что | Чем |
|-----|-----|
| CPU | `go test -cpuprofile cpu.out -bench .` → `go tool pprof -http=: cpu.out`; на живом сервисе — `net/http/pprof` |
| Куча | `go tool pprof http://host/debug/pprof/heap`; `-memprofile` в бенчмарке |
| Утечка горутин | `http://host/debug/pprof/goroutine?debug=1` — растущее число и одинаковый стек |
| Аллокации | `go test -bench . -benchmem` → `B/op`, `allocs/op` |
| Что убегает в кучу | `go build -gcflags='-m' ./...` |
| Гонки | `go test -race`, `go run -race` |
| Блокировки | `-blockprofile`, `-mutexprofile` |

`go tool pprof -base old.out new.out` сравнивает два профиля — так видно эффект правки, а не абсолютные числа.

### Типовые проблемы

**Утечка горутин** — главная в Go. Горутина, пишущая в канал без читателя или читающая из канала, который никто не закроет, живёт вечно вместе со всем стеком. Правила: у каждой горутины есть владелец, который знает, когда она закончится; отменяемая работа получает `context.Context` и проверяет `ctx.Done()`; канал закрывает отправитель; `select` с `default` или `ctx` вместо голого блокирующего чтения.

**Незакрытые ресурсы.** `defer resp.Body.Close()` сразу после проверки ошибки (без чтения тела соединение не вернётся в пул), `defer rows.Close()`, `defer f.Close()`. `time.Ticker` требует `Stop()`; `time.After` в цикле `select` создаёт таймер на каждой итерации.

**Слайс, удерживающий большой массив.** `small := big[:10]` держит весь backing array. Нужна копия — `append([]T(nil), big[:10]...)`. То же с подстрокой большой строки.

**Лишние аллокации.** `append` без `make([]T, 0, n)` при известном размере; конкатенация строк вместо `strings.Builder`; конвертация `[]byte`↔`string` в горячем пути; интерфейсное боксирование в логах. `sync.Pool` для буферов — но только после того, как профиль показал аллокации как проблему.

**Мьютекс вместо канала и наоборот.** Защита состояния — мьютекс; передача владения — канал. `RWMutex` выигрывает только при явном перевесе чтений; при коротких критических секциях он медленнее обычного.

**Карта в горячем цикле.** Хеширование строкового ключа стоит дороже, чем кажется; иногда срез с линейным поиском по десятку элементов быстрее.

## Rust

### Измерение

| Что | Чем |
|-----|-----|
| Бенчмарк | `criterion` (статистика и сравнение с прошлым прогоном) |
| CPU-профиль | `cargo flamegraph`; `perf record`/`perf report` |
| Аллокации | `dhat-rs`, `heaptrack` |
| Утечки / UB | `valgrind --leak-check=full`, Miri (`cargo +nightly miri test`) |
| Санитайзеры | `RUSTFLAGS="-Z sanitizer=address"` (nightly) |
| Асинхронные задачи | `tokio-console` — зависшие и долгие задачи |

Замеряй только `--release`: debug-сборка медленнее в разы и врёт о профиле.

### Типовые проблемы

**Циклы `Rc`/`Arc`.** Единственный способ «утечь» в безопасном Rust: два узла держат друг друга сильными ссылками и не освобождаются. Обратные ссылки — `Weak`. `Box::leak` и `mem::forget` — намеренная утечка, применяй осознанно.

**Клонирование по инерции.** `.clone()`, поставленный, чтобы «успокоить borrow checker», часто копирует `String`/`Vec` в горячем цикле. Обычно решается заимствованием, `&str` вместо `String` в сигнатуре, `Cow<'_, str>` там, где копия нужна не всегда.

**`collect()` ради промежуточного результата.** Цепочка итераторов ленива; лишний `collect` в середине материализует весь вектор. Убирай — компилятор сам всё соединит.

**Рост без `with_capacity`.** `Vec`/`String`/`HashMap` с известным размером стоит создавать с ёмкостью: иначе серия реаллокаций с копированием.

**Хешер по умолчанию.** `SipHash` устойчив к атакам, но медленный. Для внутренних карт без внешнего ввода — `FxHashMap`/`AHashMap`, выигрыш заметный.

**Блокирующий вызов в async.** Синхронный I/O или тяжёлый расчёт внутри `async fn` останавливает весь executor. Выноси в `tokio::task::spawn_blocking`. Удержание `std::sync::Mutex` через `.await` — тот же класс ошибки.

**`unsafe` ради скорости.** Только когда профиль доказал выигрыш, границы безопасности описаны комментарием, а Miri/ASAN прогнаны. В отчёт — обязательно и отдельным пунктом.

## C / C++

### Измерение

| Что | Чем |
|-----|-----|
| Утечки и обращения к освобождённому | `valgrind --leak-check=full --show-leak-kinds=all`; ASAN (`-fsanitize=address`) |
| Неинициализированное | MSAN (`-fsanitize=memory`), valgrind memcheck |
| UB | UBSAN (`-fsanitize=undefined`) |
| Гонки | TSAN (`-fsanitize=thread`) |
| CPU-профиль | `perf record -g` → `perf report`, flamegraph |
| Кеш-промахи, ветвления | `perf stat -d`, `cachegrind` |
| Куча во времени | `massif`, `heaptrack` |

Санитайзеры дают больше пользы, чем чтение кода глазами: собери отладочную конфигурацию с ASAN+UBSAN и прогони тесты — это дешёвая и очень результативная проверка.

### Типовые проблемы

**Ручное управление памятью.** В современном C++ голые `new`/`delete` в прикладном коде — почти всегда ошибка: `unique_ptr`, `shared_ptr`, контейнеры и RAII делают утечку невозможной по построению. Правило нуля: класс, который не владеет ресурсами напрямую, не нуждается в деструкторе и копирующих операциях.

**Циклы `shared_ptr`.** Два объекта держат друг друга — счётчик не доходит до нуля. Обратная ссылка — `weak_ptr`.

**Висячие ссылки и итераторы.** Ссылка на элемент `vector` после `push_back` (реаллокация), итератор после `erase`, `string_view` на временную строку, ссылка на локальную переменную из лямбды, пережившей кадр стека. ASAN ловит это в момент обращения.

**Копии в сигнатурах и циклах.** Передача контейнера по значению, `for (auto x : v)` вместо `for (const auto& x : v)`, возврат по значению без move. Проверь `-Wall -Wextra` — часть находит компилятор.

**Отсутствие `reserve`.** Рост `vector` в цикле — серия реаллокаций с копированием всех элементов.

**Раскладка данных и кеш.** На больших объёмах локальность важнее алгоритмических микроправок: обход матрицы по строкам, а не по столбцам; структура массивов вместо массива структур в горячем цикле; `vector` вместо `list`/`map`, если нет реальной нужды в их свойствах.

**Ложное разделение (false sharing).** Соседние счётчики, обновляемые разными потоками, попадают в одну кеш-линию и убивают масштабирование. Разнеси выравниванием (`alignas(64)`).

**Ключевое об оптимизации.** Компилятор `-O2`/`-O3` уже делает разворот циклов, инлайн и векторизацию. Ручные трюки чаще мешают ему, чем помогают. Правило простое: сначала алгоритм и структуры данных, потом раскладка памяти, и только потом — что-либо ещё, и только с профилем в руках.
