# Git-воркфлоу

Цель — чтобы ревьюер получил ветку с понятной историей и PR, по которому видно, что происходило, без раскопок.

## Перед началом

```bash
git status                      # чужие незакоммиченные изменения? → остановись и спроси
git remote -v                   # есть ли remote, какая платформа
git log --oneline -30           # какая конвенция сообщений уже сложилась
git branch -a                   # есть ли develop/dev
```

Базовая ветка выбирается в таком порядке: указана в плане → `develop`/`dev` → основная ветка репозитория (`git symbolic-ref refs/remotes/origin/HEAD`). `CONTRIBUTING.md` и `.github/PULL_REQUEST_TEMPLATE.md` часто отвечают на этот вопрос прямо.

```bash
git fetch origin
git checkout <база> && git pull --ff-only
git checkout -b feat/T3-login-endpoint
```

## Имена веток

`<тип>/<ID>-<слаг>` — `feat/T3-login-endpoint`, `fix/T7-worker-leak`, `perf/T12-batch-queries`.
Без ID: `fix/worker-memory-leak`. Слаг латиницей, kebab-case, 2–4 слова.

Типы: `feat` (новое поведение), `fix` (баг), `perf` (скорость/память без смены поведения), `refactor` (структура без смены поведения), `test`, `docs`, `chore`.

Если в репозитории уже есть своя схема (`feature/JIRA-123`, `KIB-45-login`) — следуй ей.

## Коммиты

Conventional Commits + ID задачи в конце заголовка:

```
<тип>(<область>): <что сделано в повелительном наклонении> [<ID>]

<Почему так, а не иначе. Неочевидные решения. Что осталось за рамками.>
```

Правила, которые реально влияют на ревью:

- **Один коммит — одно связное изменение.** Рефакторинг отдельно от функциональной правки: смешанный diff нечитаем, и ревьюер либо пропустит баг, либо потратит час.
- **Заголовок до ~72 символов**, повелительное наклонение, без точки в конце.
- **Тело — про «почему».** Что именно изменилось, видно из diff; из diff не видно, какие альтернативы отвергли и почему.
- **Не коммить сгенерированное и мусорное**: артефакты сборки, `node_modules`, `.env`, дампы, логи, временные файлы. Проверь `git status` перед `git add`, добавляй файлы явно, а не `git add -A` вслепую.
- **Не коммить сломанное состояние.** Каждый коммит должен оставлять репозиторий собираемым — иначе `git bisect` и откат по коммиту перестают работать.

```bash
git add src/api/auth/login.ts src/api/auth/login.test.ts
git commit -m "feat(auth): add JWT login endpoint [T3]" -m "Пароль проверяется через verifyPassword..."
```

## Push

```bash
git push -u origin feat/T3-login-endpoint
```

`--force` и `--force-with-lease` — только после явного разрешения пользователя. Это одна из точек остановки: чужая работа, затёртая force-пушем, не восстанавливается из локального состояния.

Push прямо в `main`/`master`/`develop` не делается никогда — вся работа идёт через PR.

## MR/PR

Платформа определяется по `git remote -v`.

**GitHub** (`gh`):

```bash
gh pr create \
  --base develop \
  --head feat/T3-login-endpoint \
  --title "Эндпоинт логина (T3)" \
  --body-file docs/reports/T3-2026-07-31.md
```

**GitLab** (`glab`):

```bash
glab mr create \
  --target-branch develop \
  --source-branch feat/T3-login-endpoint \
  --title "Эндпоинт логина (T3)" \
  --description "$(cat docs/reports/T3-2026-07-31.md)"
```

Полезные флаги, если проект их использует: `--draft` (работа не завершена), `--reviewer`, `--label`, `--assignee`. Не выдумывай reviewer'ов и метки — ставь только те, что реально есть в проекте (`gh api repos/:owner/:repo/labels`, `glab label list`).

Если в репозитории есть `.github/PULL_REQUEST_TEMPLATE.md` или `.gitlab/merge_request_templates/` — заполни шаблон проекта, а отчёт вставь в раздел описания. Шаблон обычно отражает требования ревью-процесса команды, и PR мимо него возвращают.

**CLI недоступен или нет авторизации** (`gh auth status`, `glab auth status` падают) — не пытайся авторизоваться и не проси токен. Сообщи пользователю и дай ссылку: после `git push` remote возвращает готовый URL для создания PR/MR, приведи его вместе с заголовком и телом, чтобы осталось только вставить.

## Тело PR

Тело = отчёт из `references/report-template.md`. Отдельно поверх него стоит вынести две строки, потому что их читают первыми:

```markdown
> **Что ревьюить в первую очередь:** src/api/auth/login.ts — обработка неверных учётных данных.
> **Проверено:** npm test (48 passed), npm run typecheck, npm run lint — чисто.
```

Если PR закрывает задачу в трекере, добавь ссылку в формате платформы (`Closes #42`, `Closes JIRA-123`) — она свяжет PR и задачу автоматически.

## Что делать при конфликтах

Конфликт с базовой веткой — обычное дело, если работа шла долго:

```bash
git fetch origin && git rebase origin/develop
```

Разрешай только конфликты в своих файлах. Конфликт в файле, которым владеет другая задача, означает нарушение границ — остановись и скажи об этом, не «разруливай» чужой код по своему усмотрению. Если rebase уже опубликованной ветки требует force-push — это точка остановки.
