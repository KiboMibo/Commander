# Ponytail — правила минимализма (запасной вариант)

Этот файл нужен, только когда плагин ponytail недоступен в сессии. С плагином правила приходят автоматически перед каждым ходом и соблюдаются надёжнее — предложи пользователю установить:

```
/plugin marketplace add DietrichGebert/ponytail
/plugin install ponytail@ponytail
```

Источник: https://github.com/DietrichGebert/ponytail (MIT).

## Идея

Образ, который стоит за правилами, — ленивый сеньор. Он не спорит и не читает лекций. Он пишет одну строку. Она работает.

Не потому что ленив по-настоящему, а потому что за годы понял простую арифметику: код пишется один раз, а читается, дебажится, мигрируется и объясняется новичкам десятки раз. Строка, которой нет, не сломается, не устареет и не потребует теста. Поэтому лучший ответ на задачу — тот, где кода получилось меньше всего при том же результате.

## Лестница решений

Проходи её сверху вниз перед каждым новым куском кода и останавливайся на первой подходящей ступени:

1. **Это вообще должно существовать?** → нет: пропусти. Абстракция «на будущее», флаг конфигурации, которым никто не пользуется, слой на случай смены БД, которая не сменится, — всё это YAGNI. Настоящая потребность появится, и тогда её видно целиком; выдуманная заранее почти всегда угадана неверно.
2. **Это уже есть в кодовой базе?** → переиспользуй. Самая ценная ступень. Дубликат хелпера хуже его отсутствия: копии расходятся, и баг чинят в одной из двух.
3. **Это умеет стандартная библиотека?** → используй её.
4. **Это умеет платформа нативно?** → используй её. `<input type="date">` вместо библиотеки календаря, CSS вместо анимации на JS, `Intl` вместо своего форматирования дат.
5. **Это умеет уже установленная зависимость?** → используй её.
6. **Это одна строка?** → пусть будет одна строка. Не заворачивай её в функцию, класс и модуль ради симметрии.
7. **Только теперь** — минимум, который работает.

## Что «минимум» не означает

Правила про объём кода, а не про качество. Не сокращается никогда:

- **Валидация ввода** на границах системы.
- **Проверка прав** на каждом новом входе.
- **Обработка ошибок** — не глушение, а осмысленная реакция или честное падение.
- **Доступность** — семантика, метки, фокус, контраст.
- **Понятность имён.** Однобуквенные переменные экономят символы, а не сложность.

Если сокращение задевает что-то из этого списка — это не ponytail, это баг.

## Типовые случаи переусложнения

Их стоит узнавать в лицо, потому что они выглядят как хорошая инженерия:

- **Обёртка ради обёртки.** Свой класс поверх HTTP-клиента, повторяющий его API один в один.
- **Абстракция под один случай реализации.** Интерфейс с единственным наследником, фабрика, создающая один тип.
- **Конфигурация без потребителя.** Параметр, который всегда передают одним и тем же значением.
- **Обработка невозможного.** Ветка для случая, который не может произойти при текущих типах.
- **Библиотека вместо трёх строк.** Зависимость ради `capitalize`, `debounce` или форматирования даты.
- **Ранняя оптимизация.** Кеш, пул и мемоизация до того, как замерена реальная проблема. (Обратное — игнорировать замеренную проблему — такая же ошибка.)
- **Комментарии, пересказывающие код.** `// увеличиваем счётчик` над `count++`.
- **Преждевременная общность.** Функция с семью параметрами «чтобы подошла и для будущих случаев».

## Маркер в коде

Когда решение выглядит подозрительно простым и следующий читатель захочет «доделать» — оставь одну строку, объясняющую, почему проще не надо:

```html
<!-- ponytail: браузер уже умеет это сам -->
<input type="date">
```

```python
# ponytail: dict.get с дефолтом покрывает все ветки, отдельный класс не нужен
```

## Когда правило уступает

Ponytail — про то, чтобы не делать лишнего, а не про то, чтобы не делать нужного. Явное требование из плана, конвенция проекта и архитектурное решение из `/coding-architect` имеют приоритет: если план требует слой абстракции, значит для него была причина, которой не видно из одной задачи. В таком случае следуй плану, а сомнение вынеси в отчёт — там ему место.
