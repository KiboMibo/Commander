# Производительность и память: TypeScript / JavaScript / Node

Порядок работы всегда один: **воспроизведи → измерь → почини → измерь снова**. Догадка о причине тормозов ошибается чаще, чем угадывает, а «оптимизация» без замера обычно добавляет сложность и ничего не ускоряет. Оба числа — до и после, полученные одинаково — идут в отчёт.

## Измерение

| Что выясняем | Чем |
|--------------|-----|
| Где уходит CPU | `node --cpu-prof app.js` → профиль в DevTools; `clinic flame` |
| Что держит память | `node --inspect` → Memory → Heap snapshot; `clinic heapprofiler` |
| Рост памяти во времени | RSS через `process.memoryUsage()` с интервалом; три снапшота и сравнение |
| Задержки event loop | `perf_hooks.monitorEventLoopDelay()`; `clinic doctor` |
| Пропускная способность HTTP | `autocannon -d 30 -c 50 <url>` |
| Микробенчмарк функции | `node --expose-gc` + `performance.now()` на прогретом коде; `mitata` |
| Вес бандла (фронт) | `source-map-explorer`, `vite-bundle-visualizer`, Lighthouse |

**Метод трёх снапшотов** для поиска утечки: снимок → нагрузка → снимок → та же нагрузка → снимок. В DevTools сравни второй и третий в режиме «Objects allocated between snapshots». То, что живёт после второй нагрузки и растёт, — кандидат. Колонка Retainers показывает, кто держит ссылку.

## Типовые причины утечек

**Слушатели без снятия.** `addEventListener`, `emitter.on`, подписка на observable, `process.on` — каждая подписка держит замыкание, а через него весь захваченный контекст. В долгоживущем процессе `emitter.on` внутри обработчика запроса — это утечка в чистом виде. Признак в Node: предупреждение `MaxListenersExceededWarning`.

**Таймеры и интервалы.** `setInterval` без `clearInterval` живёт вечно и держит всё, до чего дотягивается замыкание. `setTimeout` в цикле переподписки — то же самое.

**Кеш без границ.** `Map`/объект, куда пишут по ключу запроса и никогда не удаляют. Лечится ограничением размера (LRU) и TTL. Если ключ — объект и его допустимо собрать сборщику, подходит `WeakMap`/`WeakSet`: они не удерживают ключ.

**Замыкание, удерживающее лишнее.** Функция, которой нужно одно поле большого объекта, но захватывает она объект целиком, — и объект не собирается, пока жива функция. Достань нужное поле в переменную до создания замыкания.

**Глобальное накопление.** Массив логов/метрик/истории на уровне модуля, в который дописывают и не чистят. В скрипте безобидно, в сервисе — падение через сутки.

**Оторванные DOM-узлы (фронт).** Удалили узел из документа, но на него осталась ссылка в переменной, в замыкании обработчика или в стороннем виджете. В снапшоте видны как `Detached HTMLDivElement`.

**Непрочитанные потоки.** Открытый `ReadableStream`, неразрешённый `pipeline`, соединение, не возвращённое в пул. Проверяй парность: `open`↔`close`, `acquire`↔`release`.

## Типовые причины медленного кода

**Линейный поиск внутри цикла.** `arr.find`/`includes`/`indexOf` в теле цикла по другому массиву — `O(n·m)`. Построй `Map`/`Set` один раз до цикла: станет `O(n+m)`. Это самая частая находка в профиле.

**Запрос в БД или HTTP внутри цикла (N+1).** Замени батчем (`WHERE id IN (...)`, `dataloader`), join или предзагрузкой. Здесь выигрыш измеряется не процентами, а порядками.

**Последовательный `await` там, где нужен параллельный.** Цикл с `await` внутри выполняет запросы по очереди. Если они независимы — `Promise.all` (или `Promise.allSettled`, если частичный отказ допустим). Осторожно с неограниченным параллелизмом на тысячах элементов: нужен пул (`p-limit`).

**Пересоздание тяжёлого на каждом вызове.** Компиляция регулярного выражения, `new Intl.NumberFormat`, подключение к БД, разбор конфига — вынеси на уровень модуля.

**Копирование в цикле.** `arr = [...arr, x]` и `obj = {...obj, k}` внутри цикла дают квадратичную сложность. Мутируй локальный аккумулятор и заморозь результат один раз, если нужна неизменяемость снаружи.

**Синхронная блокировка event loop.** `JSON.parse` гигантской строки, `crypto.pbkdf2Sync`, `fs.readFileSync`, тяжёлая регулярка в обработчике запроса — блокируют весь процесс. Асинхронные аналоги, `worker_threads` для CPU-задач, потоковый разбор для больших данных.

**Катастрофический бэктрекинг в регулярках.** Вложенные квантификаторы (`(a+)+`) на неудачном входе вешают процесс. Признак — CPU 100% на одном запросе. Проверь выражение на ReDoS, перепиши без вложенных повторов.

**React-специфичное.** Новый объект/массив/функция в пропсах на каждом рендере ломает мемоизацию; тяжёлые вычисления в теле компонента без `useMemo`; список без стабильного `key`; контекст, меняющийся на каждом рендере родителя. Перед оптимизацией — React DevTools Profiler: он показывает, какой компонент реально ререндерится и почему.

## Чего не делать

Микрооптимизации уровня «`for` быстрее `forEach`» дают проценты там, где рядом лежит N+1 с трёхкратным запасом. Сначала находи большое в профиле. И не жертвуй читаемостью ради выигрыша, которого не видно в замере, — это чистый убыток.
